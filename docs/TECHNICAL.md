# How GladiusPort works

This page explains what happens between the retail Xbox `default.xbe` and a game running on Windows: how the
executable is converted, how the Xbox kernel and system libraries are replaced, and how the Direct3D 8 → Direct3D 11
layer renders the game and adds its visual upgrades.

## Overview

```
retail default.xbe ──► tools/xbe2pe.py ──► gladius.exe   (original x86 code at its original addresses)
                                              │
                                              │  former kernel / XAPI / D3D8 / DirectSound / XInput calls
                                              ▼
                                       gladiusport.dll ──► Direct3D 11, WASAPI, XInput / SDL2, files
```

The Xbox runs ordinary 32-bit x86 code, so the game's own code can run on a PC as it is. What can't run is
everything around it: the Xbox kernel, the XAPI system library, Direct3D 8 for the NV2A GPU, DirectSound for the
MCPX audio chip and the controller libraries. GladiusPort keeps the game code and swaps out all of those.

There is no CPU emulation: the game's instructions run natively. The system libraries are reimplemented at their
API level, which is often called high-level emulation (HLE). The GPU, audio chip and kernel are never modelled at
the hardware level. The closest the port comes is the renderer, which decodes the NV2A commands the engine writes
into its push buffer and maps them onto Direct3D 11 state.

## 1. XBE → PE conversion

`tools/xbe2pe.py` rebuilds `default.xbe` as a Windows PE executable.

- **Same addresses.** The image base is `0x10000`, the XBE's own base, so every section keeps its original virtual
  address. No code is relocated or rewritten, and every address in the game (functions, globals, vtables) means
  the same thing on the PC.
- **Kernel thunks become imports.** The XBE's kernel thunk table, the list of 162 kernel functions and data
  exports the game links to, becomes the import address table for `gladiusport.dll`. Each slot imports one
  `krnl_*` export, so the Windows loader fills the table exactly where the game expects it.
- **TLS.** The XBE's thread-local storage block becomes a PE TLS directory. The Windows loader ignores a TLS
  zero-fill size, so the zero fill becomes an explicit zeroed template.
- **`.port` section.** A small section holds the startup stub, the trampolines for replaced functions, copies of
  the XBE section headers (`XGetSectionHandle` returns them), a stand-in for the Xbox thread block the C runtime
  reads, and an info block passed to the DLL.
- **Icon.** The XBE's title image becomes the exe's icon.

At startup, `gladiusport.dll` runs the game's runtime initialisation (CRT init tables, C++ static constructors,
FPU setup) in the original order, then calls the game's `main`.

## 2. Function replacement

The Xbox SDK libraries (XAPI, Direct3D 8, DirectSound, XGraphics, the controller code) are **statically linked**
into `default.xbe`; the game calls them like its own functions. Their entry points were identified from library
signatures (the [XbSymbolDatabase](https://github.com/Cxbx-Reloaded/XbSymbolDatabase) project) and are listed in
`tools/replacements.py` and `tools/d3d_table.py`.

`xbe2pe.py` overwrites the first five bytes of each one with a `jmp` into `.port`, which jumps through a second
import table into `gladiusport.dll`. That covers 236 XAPI and system functions, 88 Direct3D 8 entry points and 39
DirectSound entry points. Each replacement keeps the original calling convention and argument layout, so callers
can't tell the difference.

The code LucasArts wrote, the engine and the game logic, is not modified by the conversion. A short list of byte
patches (`replacements.PATCHES`) only fixes places where Xbox-specific code would fail on a PC.

## 3. Kernel replacement

There is no Xbox kernel in the converted exe. Because the system libraries are replaced from above, almost no
game code talks to the kernel directly anymore. The 162 kernel import slots are generated by
`tools/gen_krnl_exports.py` into `src/krnl_exports.cpp` and fall into three groups:

| Group | Count | What the export is |
|---|---|---|
| **Implemented** | 8 | The few kernel functions game code and the C runtime call directly: critical sections (`src/critsec.cpp`) and time conversions (`src/krnl_time.cpp`). |
| **Data** | 20 | Kernel data exports (object types, hardware info, key data, the launch data page): zeroed placeholder blocks. |
| **Traps** | 134 | Anything else. Calling one logs the kernel function's name and the caller's address. A trap means a library function was missed, so in practice they never fire. |

**Critical sections on the Xbox layout.** Game code initialises some critical sections statically in its data, in
the Xbox kernel's 28-byte `RTL_CRITICAL_SECTION` format, which differs from Windows. `critsec.cpp` implements them
on that exact layout, with an event for contention.

**Threads behave like on a single-core Xbox.** On the Xbox, a new thread doesn't run until its creator blocks or
yields, and the engine relies on that. Game threads start suspended and are released at their creator's next wait,
sleep, yield or present (or after 50 ms). The CRI movie and audio middleware locks itself by raising thread
priority, which excludes nothing on a multi-core PC; `src/cri_lock.cpp` replaces that with a real lock that is
released whenever its owner blocks.

**Timing.** The engine reads the CPU timestamp counter directly and converts with the Xbox's 733 MHz frequency.
On the PC, the performance counter is the timestamp counter and its frequency is this machine's measured rate, so
both stay on one clock. A timer thread provides the 59.94 Hz video interrupt the engine and movies pace
themselves on.

**Soft reboot.** Where the Xbox relaunches `default.xbe` (leaving the world map, quitting to the menu), `XLaunchNewImage`
starts a fresh `gladius.exe` with the launch data and window position. The new window takes over on its first
frame and the old process exits, so the switch is seamless.

**Diagnostics.** `port.log` records startup, every trap and every crash (with a full memory dump). A watchdog
reports stuck threads.

## 4. XAPI on Windows

The XAPI replacements keep the Win32-style signatures the Xbox used, so most map straight onto Windows.

- **Files and drives.** Xbox drive letters map to folders: `D:` (the disc) to the game folder; `U:`, `T:` and `Z:`
  (saves, title data, cache) to the save folder. Saves are plain files in the original Xbox format.
- **Memory.** Xbox "physical" memory (memory the GPU and audio chip can see) is ordinary memory on a PC, because
  Direct3D and DirectSound are replaced too.
- **Memory container.** The game's heap and physical memory can live in fixed, reserved address ranges managed by
  [dlmalloc](https://gee.cs.oswego.edu/dl/html/malloc.html) mspaces. dlmalloc is deterministic, so the game's
  memory is laid out identically on every PC. Online versus relies on this to copy game state between machines.
- **Virtual handles and thread ids.** The game never receives a real Windows handle or thread id; it gets stable
  virtual values instead, so the contents of game memory are identical across machines too.
- **Dashboard settings and saves.** Language, video mode, parental controls and disk geometry return fixed PC
  values, and memory units report as absent (only the "hard disk" exists).
- **Shader assembly.** The engine generates its shaders as assembly text and assembles them at runtime
  (`XGAssembleShader`). The replacement keeps the source text and hands back a placeholder tagged with its hash, so
  the renderer knows which shader is meant (see below).

## 5. Direct3D 8 → Direct3D 11

The Xbox Direct3D 8 is not the PC Direct3D 8. It is a thin layer over the NV2A GPU: the engine writes NV2A
**push-buffer** commands directly, keeps resources in Xbox-specific formats (swizzled and DXT textures in
physical memory) and builds its own vertex and pixel shaders. GladiusPort implements this API on Direct3D 11. No
`d3d8.dll` is involved.

### State: one NV2A state table

Render states set through the API and push-buffer commands the engine writes itself both speak NV2A methods. The
push buffer is decoded and everything lands in one NV2A state table, from which Direct3D 11 blend, depth and
rasterizer objects are built at draw time and cached. Bound state is tracked so each draw only sets what changed.

### Resources

Resource headers keep the Xbox layout the game reads and writes. Textures are found by their content (address,
format, size), converted from Xbox formats (swizzled, DXT, movie YUY2) and re-uploaded when the game
rewrites their memory. Vertex and index data are cached on the GPU in chunks and only re-uploaded when the bytes
change.

### Shaders: translation, not emulation

The engine writes its shaders at runtime as Xbox vertex shader assembly (`xvs.1.1`) and NV2A register-combiner
pixel assembly (`xps.1.1`). Instead of emulating the GPU's microcode, `src/shader_translate.cpp` translates that
source text into **HLSL (shader model 4)**:

- vertex inputs are decoded per the draw's vertex attribute formats;
- the 192 Xbox constants, address register and screen-space programs are mapped one to one;
- register-combiner instructions (`xmma`, `xdm`, final combiner and the rest) become plain HLSL arithmetic.

Compiled shaders are cached in `build\shadercache`, so a shader only compiles the first time it is ever seen.

### Resolution and widescreen

The engine hard-codes 640×480 in many places. `src/game_resolution.cpp` rewrites every one of them at startup,
so the game renders at any resolution:

- 3D widens horizontally (Hor+);
- the 2D layer follows the chosen UI aspect and screen fit;
- the character previews in the school and shop screens keep their original framing;
- render scale can supersample the scene up to 4×.

### Frame structure

Each frame renders the 3D scene into an HDR target alongside a small **G-buffer**:

- **depth**, for SSAO, shadows and soft particles;
- **per-pixel motion**, for TAA.

When the engine starts its 3D particle pass, the opaque scene is complete. At that point shadows and SSAO are
applied. Once the 3D scene is finished, TAA resolves it before any 2D is drawn, so the HUD and menus never smear.
A final pass then applies bloom, colour grading and tone mapping, and scales the image to the window.

## 6. Visual enhancements

Every enhancement is optional and can be changed in the in-game **Video** options page, with hotkeys or in
`gladiusport.ini`. With all of them off, the game looks like the Xbox original at a higher resolution.

**HDR rendering.** The scene is rendered into a 16-bit floating-point target, so stacked additive effects and
lighting extras can exceed white. Tone mapping shows everything up to white exactly as authored and rolls brighter
light toward white while keeping its hue.

**Per-pixel lighting.** The translator recognises the lighting code the engine generates (ambient, emissive and a
list of directional lights) and evaluates it per pixel instead of per vertex, adding specular, rim light and
surface relief (bump detail). Surfaces with baked or ambient-only lighting can be **relit** by the sun.

**Sun shadows.** Gladius only has blob shadows. GladiusPort records every opaque draw that casts during the frame,
replays them from the sun (the brightest light in the engine's light list) into a shadow map, and darkens occluded
pixels in a full-screen pass. The map size is selectable up to 8192².

**Ambient occlusion (SSAO).** Half-resolution AO from the G-buffer depth, blurred with depth awareness and applied
to the opaque scene only, so particles and 2D stay undarkened.

**Soft particles.** Particle draws read the scene depth and fade where they meet geometry instead of cutting hard
lines into it.

**Effect lights.** Additive particle draws (fire, sparks, spell glows) become light sources at their centre,
coloured by their texture. The four strongest each frame light the characters and relit surfaces around them.

**Material effects.** Surfaces get effects by texture asset name: rippling water, glowing lava, flickering
glowing props, swaying foliage and cloth.

**Bloom and god rays.** Thanks to the HDR scene, only light that is actually overbright blooms (spell cores, lava,
sun glints), through a downsample/upsample chain. God rays shine from the sun.

**Anti-aliasing.**
- **FXAA:** a fast edge filter at scene resolution.
- **TAA:** 3D draws are jittered by a sub-pixel Halton offset over 8 frames, and the previous frames are blended
  in. Every engine draw's vertex shader also runs on that draw's constants from the previous frame, so each pixel
  knows exactly where it was last frame, including for spinning and animated models. Pixels without that fall back
  to the camera's motion. History is clamped to the current neighbourhood to prevent ghosting.

**Render scale.** 1×–4× supersampling, or Auto. The final pass averages every texel an output pixel covers, so
downscaling doesn't shimmer.

**Colour grading.** Saturation, contrast, warmth and vignette.

**HD texture replacement.** A folder of PNGs named after the original textures replaces them at load time. A
background job decodes each one and checks it shows the same picture as the original. It rebuilds padded layouts
at the new scale, builds mipmaps and swaps the texture in when it's ready, so loading never stalls. F4 toggles
between original and HD.

**Presets and hardware detection.** Low, Medium and High presets. The builder and the game detect the GPU, CPU
cores and monitor and recommend one.

## 7. Audio, movies and input

**Audio.** DirectSound is replaced by a software mixer feeding WASAPI. Sound buffers (PCM or Xbox ADPCM) and
streams are decoded, resampled, mixed with their volume and speaker mix, and reported back with real playback
positions.

**Movies and music.** The CRI Sofdec (video) and ADX (audio) middleware run their original code; their frames go
through the renderer, scaled to the chosen resolution.

**Controllers.** SDL2's game controller API supports Xbox, PlayStation 3/4/5, Switch Pro and every controller
in SDL's database through one layout, with hot-plugging. Windows XInput is the fallback when SDL2 is missing. The
keyboard drives player 1.

## 8. Game additions

These are small hooks into the game's own screens and systems.

- **Video options page** next to the game's own options (reusing the retail options menu).
- **27 save slots** instead of 3, paged on the save and load screens.
- **Quit Game** in the main menu.
- **Versus unlocks**: Versus from the start, all 15 versus arenas.
- **Developer menus** from the original game data, re-enabled (optional).
- **Online versus** in `netplay/gladiusnet.dll`. It runs on a deterministic mode in `gladiusport.dll`: fixed
  frame time, fixed AI iterations and finished reads before each frame. Every machine runs the same frames from
  the same inputs.
- **Level editor** (optional, `gladius_editor.exe`): live prop, mesh, collision and battle-grid editing. See
  [EDITOR.md](EDITOR.md).
